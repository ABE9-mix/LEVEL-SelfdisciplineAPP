## 1. 资源分层：三条不能越的边界

```
┌─ 永久层（任何失败都不动）──────────────┐
│ XP · Level · 称号 · 徽章 · 任务历史      │
│ 累计活跃天数 · 真实产出（时长/次数）      │
└──────────────────────────────────────┘
┌─ 已结算层（失败不动）──────────────────┐
│ 已结算魂火（阶段仪式上确认过的）          │
│ 含：恢复挑战追回的魂火                    │
└──────────────────────────────────────┘
┌─ 暂存层（唯一会被扣的）────────────────┐
│ 未结算魂火 = 本轮已得 − 已结算            │
└──────────────────────────────────────┘
```

三条硬边界：

1. **惩罚只作用于暂存层**。任何规则不得回头扣 XP、降等级、撤称号、删历史。
2. **已结算不可逆**。一旦在篝火结算仪式上确认，永久留在已结算层。
3. **损失是计算出来的，不是估计的**。失败页上的每一个数字都必须能在账上复算（见 §6.3）。

## 2. 魂火从哪来：任务权重与产出

魂火不是"做题得分"，是**真实投入的换算**。所以它挂在任务权重上，不挂在打卡动作上。

### 2.1 权重表

| 权重 | 判定标准（满足其一） | XP | 魂火 |
|---|---|---|---|
| **轻** | 预计 ≤15 分钟；或单次一次性动作 | 20 | 5 |
| **中** | 15–45 分钟；或需要连续投入 | 40 | 10 |
| **重** | >45 分钟；或有硬性产出（写完/跑完/交付） | 60 | 15 |

**换算关系：魂火 = XP ÷ 4**。这条固定，避免出现两套并行膨胀的数值。

### 2.2 产出的三个前提

一个任务只有在满足全部三条时才产生魂火：

1. **有完成标准**（不是"学习英语"，是"精听 25 分钟"）
2. **有实际值**（打卡时填写真实数字：25 分钟 / 20 个 / 2 公里）
3. **过了合理性下限**（低于设定值 60% 记"部分完成"，只给 50% 魂火，不给 XP 折扣）

第 3 条是防自欺的：**没有这一条，整套奖惩就没有意义**（见 §9）。

### 2.3 一轮的魂火池

```
本轮魂火池 = Σ(本轮每个任务的魂火)
```

例：深渊 5 天 × 每天 3 项中任务 = 15 × 10 = **150 魂火池**。

这个数决定后面所有损失、追回、动画亮度的分母。

## 3. 三种模式参数总表

| 参数 | 旅者 Traveler | 骑士 Knight | 深渊 Abyss |
|---|---|---|---|
| **阶段长度** | 7 天 | 7 天 | 5 天 |
| **每日任务上限** | 5 | 5 | 4 |
| **结算门槛** | 无（全额结算） | 完成率 ≥ 85% | 完成率 = 100% |
| **未达门槛 → 损失比例** | 0% | 30% | 100% |

| **休息日额度** | 3 天 / 轮（可自设 0–3） | 2 天 / 轮（可自设 0–2） | 1 天 / 轮，**须在开始前指定日期** |
| **暂停** | 不限次，单次 ≤7 天 | ≤2 次，单次 ≤3 天，累计 ≤5 天 | ≤1 次，单次 ≤2 天，累计 ≤2 天 |

## 4. 深渊模式专章

### 4.1 只有两种结局

深渊没有"部分成功"。一轮结束时只有两个状态：

- **完成**：完成率 100% → 本轮魂火池全额结算，进入已结算层
- **熄灭**：任一失败条件触发 → 未结算魂火 × 100% 失落

这条决定了深渊的性格：**它不是更难的骑士，它是另一个赌注结构**。

### 4.2 魂火损失比例：为什么是 100%

原文档写的是「可能失去全部未结算魂火」。这个「可能」我按最严格解读落地，理由三条：

1. **模式的辨识度来自损失结构，不来自难度数字**。如果深渊只扣 60%，它和骑士（30%）的差别就变成"扣得多一点"，用户感知不到结构差异。
2. **部分损失会制造更糟的情绪**。扣 60% 时用户会算"我还能拿回 40%"，注意力从"我为什么失败"转移到"我还剩多少"，这是最差的一种失败体验。
3. **100% 才配得上 40% 的追回**。全失 + 可追回 40% = 有救但代价真实。若只失 60%，追回 40% 就变成"几乎没损失"。

**已结算魂火、XP、称号、历史记录，一分不动**。深渊拿走的是"这一轮还没兑现的期待"，不是"你这个人"。

### 4.3 四条失败判定

判定时点在**日切 04:00**（见 §4.5）。四条任一成立即进入熄灭流程：

| 编号 | 条件 | 判定时点 | 触发后的火焰表现 |
|---|---|---|---|
| **F1 断档** | 连续 2 个日切完成 0 项（非休息日、非暂停日） | 第 2 个日切 04:00 | 火焰先骤降 40%，再熄灭 |
| **F2 裂痕满** | 未修复裂痕累计 > 2（即第 3 次） | 产生第 3 次裂痕的日切 | 闪烁 1.2s 后熄灭 |
| **F3 末日未满** | 阶段末 04:00 完成率 < 100% | 阶段末 04:00 | 缓慢熄灭（2.4s 完整版） |
| **F4 主动退出** | 用户点击"结束本轮"并二次确认 | 即时 | 熄灭但保留结算动画，文案不同 |

**F4 是必须有的**。没有主动退出，深渊就变成"只能等它杀你"，用户会用卸载来表达退出——那才是真正的流失。

### 4.4 四道缓冲：休息、暂停、补录、补做

这是全文档最容易被糊成一团的部分。四件事必须在数据结构上分开，不能共用"未完成"一个状态。

| 机制 | 用户做了什么 | 系统怎么记 | 对深渊的影响 |
|---|---|---|---|
| **休息日** | 事先声明今天不练 | 当天不生成任务；不计入分母 | 无裂痕、无损失 |
| **暂停** | 突发事件，暂停整轮 | 不计入分母；**截止日顺延** | 无裂痕、无损失；额度用尽后不可再暂停 |
| **补录** | 做了但忘了打卡 | 视为**按时完成**，无任何痕迹 | 无裂痕、无损失 |
| **补做** | 当天确实没做，之后补上 | 当日记 1 裂痕 → 完成后**裂痕清除**，完成率补回 | 裂痕计数归零，但"补做次数"记入档案 |

四条的时间窗：

```
任务到期时刻 ──┬── 补录窗口 24h ────────────→ 补录截止
              ├── 日切 04:00 → 记裂痕 ──┬── 补做窗口（深24h/骑36h/旅48h）──→ 补做截止
              │                          └── 未补做 → 裂痕转为"未修复"
              └── 断档计数 +1（当日 0 项且非休息/暂停）
```

**损失的分母是「已得魂火」，不是「魂火池分」。** 没完成的任务从未产生魂火，自然也不在损失范围内。魂火池只用作火焰高度的分母（见 §7.2），不参与结算。

**深渊的 0 次计划调整**是刻意的：深渊卖的就是"你承诺了就不改"。但开始前的计划设置界要因此提供更强的帮助（预估耗时、冲突提醒），否则这条规则会变成陷阱。

**深渊的 1 个休息日必须在开始前指定具体日期**，不能在当天临时用。理由：临时休息会让"深渊"退化成"随时可以停的骑士"；预先指定则保留了"我提前安排了休息"的承诺感。

### 4.5 深渊的一天（时间轴）

```
04:00  日切
       ├─ 生成当日任务（若为休息日/暂停日则跳过）
       ├─ 结算昨日：有未完成 → 裂痕 +1
       ├─ 检查 F1（连续 2 天 0 完成）→ 触发熄灭
       └─ 检查 F2（未修复裂痕 ≥3）→ 触发熄灭
04:00–次日04:00  执行
       任务完成 → 魂火 +XP +粒子汇入
       裂痕在补做窗口内被清 → 裂痕 -1
04:00  阶段末 → 检查 F3（完成率 <100%）→ 触发熄灭
```

### 4.6 恢复挑战：条件、期限、追回

**发起条件**（全部满足）：

1. 本轮已判定熄灭（F1/F2/F3/F4 任一）
2. 距离熄灭 ≤ **48 小时**
3. 本次熄灭尚未发起过恢复挑战（每轮 1 次）
4. 当前无未完成的另一场恢复挑战

**恢复任务怎么生成**：

```
可追回上限 = 损失魂火 × 40%        （向下取到 5 的倍数）
恢复任务数 N = clamp(ceil(可追回上限 ÷ 25), 1, 4)
每个任务追回 = 可追回上限 ÷ N      （最后一个补齐余数）
```

任务内容优先取：**失败当日未完成的任务** → 本轮其他未完成任务 → 用户自选同权重任务。不凭空造新负担。

**发放方式：线性，完成一个发一个**。

以「损失 120 → 可追回 50 → N = 2」为例：

| 完成 | 追回 | 占可追回上限 | 重燃终点亮度（= 追回 ÷ 损失） |
|---|---|---|---|
| 1/2 | 25 | 50% | 0.21 |
| 2/2 | 50 | 100% | 0.42 |

注意最后一列：**即使拿满追回上限，火焰也只回到 42%，不会满血**。这就是规则在视觉上的暴露点。

**追回的魂火直接进入已结算层**——它已经是"用真实行动换回来的"，不该再有第二次失去的机会。这也是"深渊失败后不至于一无所获"的唯一底线。

**恢复失败（到期未完成）**：

- 未追回的部分永久失去
- **不叠加任何惩罚**：不扣 XP、不延长冷却、不降低下轮额度
- 不消耗称号资格（"深渊归来者"只看是否重新完成一个阶段）

**与新一轮的关系**：可以并行。恢复任务照常给 XP，但**只归还魂火，不产生新魂火**（否则等于同一份努力记两次）。

### 4.7 深渊的完整数值示例

```
设定：5 天，每天 3 项中任务（10 魂火 / 40 XP）
魂火池 = 15 × 10 = 150

第 1–2 天全完成：魂火 60
第 3 天：完成 2/3，缺 1 项，未在 24h 内补做 → 裂痕 1
第 4 天：完成 3/3，补做了第 3 天缺的项 → 裂痕清除，完成率补回
第 5 天：完成 3/3 → 完成率 100%

结局：完成 → 结算 150 魂火（全部进入已结算层）
```

```
变体：第 3、4、5 天各缺 1 项且均未补做 → 裂痕 3
已得魂火 = 12 项 × 10 = 120（缺的 3 项从未产生魂火，不在损失范围）
结局：F2 触发，第 5 天日切熄灭
损失 = 120 × 100% = 120
可追回 = round5(120 × 40%) = 50，N = clamp(ceil(50/25),1,4) = 2，每项 25
用户两项都完成 → 追回 50，直接进入已结算层
最终：失落 70，已结算 50，XP 与历史记录全额保留
熄灭后余烬 = clamp(round(50/20),1,12) = 3 粒
重燃终点亮度 = 50 ÷ 120 = 0.42
```

## 5. 骑士与旅者：同结构，不同压力

### 5.1 骑士

- 结算门槛 85% → 一轮 21 项里容许缺 3 项
- 未达门槛：损失 30%（而非 100%），**损失的 50% 可通过恢复追回**
- 裂痕上限 4，超过才熄火
- 文案基调：责任，不说狠话。「失去的魂火可以追回，失去的决心也能重燃。」

算例：21 项，完成 17 项（81%）→ 未达门槛 → 已得魂火 170 → 损失 round5(170×30%) = 50 → 可追回 round5(50×50%) = 25。

### 5.2 旅者

- **不熄火**，不设裂痕上限，只记录
- 阶段结束**一律全额结算**，完成率不影响任何资源
- 完成率只影响：阶段徽章（≥70% 铜 / ≥85% 银 / 100% 金）与称号进度

这一条是刻意的：旅者的承诺是"不惩罚"，一旦引入任何折扣，它就不再是低压力入口。

### 5.3 三种模式的仪式强度

| 节点 | 旅者 | 骑士 | 深渊 |
|---|---|---|---|
| 点燃 | 0.8s 微光 | 2.0s 稳定 | 3.0s，黑场中单点火种 |
| 达标的普通任务 | 0.3s 亮光 | 0.6s 粒子汇入 | 0.6s，暗场中闪现 |
| 阶段完成 | 3s 温暖 | 6s 庄严 | 8s，限一次/轮 |
| 熄灭 | 不触发 | 2.4s 渐弱 | 3.2s 完整熄灭 + 余烬 |
| 重燃 | 不触发 | 2.4s | 3.0s 三段 |

## 6. 判定引擎

### 6.1 日结算伪代码

```js
// 每日 04:00 执行，对每场进行中的挑战
function dailySettle(challenge) {
  const day = challenge.today                       // 昨日
  if (day.isRest || challenge.paused) return        // 休息/暂停 → 直接跳过，不记任何东西

  const due = day.tasks
  const done = due.filter(t => t.completed)         // 含补录
  const late = due.filter(t => t.doneByMakeup)      // 补做不算当日按时

  if (done.length === 0) challenge.zeroDayStreak++  // F1 计数
  else challenge.zeroDayStreak = 0

  const unfixed = due.filter(t => !t.completed && !t.doneByMakeup)   // 当日未完成
  if (unfixed.length > 0) challenge.cracks.push({ day, items: unfixed })  // 裂痕 +1

  // 补做窗口到期后，未补做的裂痕转为"未修复"
  challenge.cracks = challenge.cracks.filter(c =>
    c.fixed || within(c.createdAt, MODE[challenge.mode].makeupWindow))

  checkFailure(challenge)   // F1 / F2
}
```

### 6.2 阶段末判定

```js
function stageEnd(challenge) {
  const total = challenge.tasks.length
  const completed = challenge.tasks.filter(t => t.completed || t.doneByMakeup).length
  const rate = completed / total
  const m = MODE[challenge.mode]

  if (challenge.mode === 'traveler') return settle(challenge, 1)        // 全额
  if (rate >= m.threshold)           return settle(challenge, 1)
  return settle(challenge, 1 - m.loss)                                  // 骑士 0.7 / 深渊 0
}
```

### 6.3 损失必须可复算

失败页展示的每一个数，都要能用同一套公式复算出来。这就是原文档 §3.3 和 §19.2 的要求落到工程上的样子：

```
未结算魂火 = Σ(已完成任务的魂火) − 已结算魂火
损失       = round5(未结算魂火 × 损失比例)
可追回上限 = round5(损失 × 追回比例)
实际追回   = Σ(已完成的恢复任务各自应追回)
```

### 6.4 八个边界案例

| 场景 | 判定 | 理由 |
|---|---|---|
| 23:50 开始，00:10 打卡 | 记在**昨日**，按时完成 | 日切是 04:00，不是 00:00 |
| 完成了但忘了打卡，次日 10:00 补录 | 按时完成，无裂痕 | 补录窗口 24h 内 |
| 补录窗口过了才想起来 | 记裂痕，可在补做窗口内补做 | 两件事分开处理 |
| 计划内休息日却做了一项 | 记为"额外行动"，**不进分母** | 进分母会拉低完成率，惩罚了多做 |
| 暂停跨过阶段末日 | 截止日顺延，不判失败 | 暂停的定义就是"时间停止" |
| 一轮里减了 2 次任务（骑士） | 允许，以**最新计划**为分母，旧版本存档 | 调整是合法的，但不能靠减任务刷完成率 |
| 深渊中减任务 | 拒绝，提示"深渊不支持调整计划" | 深渊的核心承诺 |
| 恢复挑战做了一半就到期 | 追回已完成部分，其余作废 | 不叠加惩罚 |

## 7. 篝火状态机 → 动画映射

这是这套规则存在的意义：**每个动画参数都是某个规则数值的函数**。

### 7.1 九个状态

| 状态 | 进入条件 | 火焰 | 环境 | 时长 |
|---|---|---|---|---|
| `DORMANT` | 无进行中挑战 | 冷灰，无粒子 | 无光 | — |
| `IGNITING` | 接受挑战并确认风险 | 单点火星 → 稳定 | 由暗到 40% | 2.0s（旅者 0.8s） |
| `BURNING` | 进行中，未修复裂痕 = 0 | 稳定，粒子持续汇入 | 100% | 持续 |
| `LOW` | 未修复裂痕 ≥ 1 | 亮度 ×(1 − 0.12×裂痕)，火焰高度 −15% | 90% | 持续 |
| `FLICKER` | 未修复裂痕 = 上限，或 剩余任务 > 剩余天数 × 日均 | 1.2Hz 闪烁，边缘风动 | 82%，偏冷 8% | 持续；每日首次进入播 1.2s |
| `SETTLING` | 阶段完成 | 升高 → 汇聚 | 120% 短暂过曝后回落 | 5–8s 可跳过 |
| `EXTINGUISHING` | 判定失败 | 渐弱 → 余烬 | 由 100% 降到 20% | 2.4s（深渊 3.2s）可跳过 |
| `EXTINGUISHED` | 失败后，未重燃 | 只剩余烬 | 冷灰 | 持续 |
| `REKINDLING` | 恢复/重燃后完成第一个任务 | 余烬 → 微光 → 火焰 | 20% → 由参数决定 | 3.0s |

### 7.2 规则数值如何驱动动画

| 动画参数 | 公式 | 意义 |
|---|---|---|
| 稳定态火焰高度 | `0.6 + 0.4 × (当前魂火 ÷ 本轮魂火池)` | 火有多大 = 这轮积累了多少 |
| 粒子汇入数量 | `round(魂火 ÷ 20)`，封顶 12 | 完成一次任务，火真的变旺一点 |
| `LOW` 亮度系数 | `1 − 0.12 × min(未修复裂痕, 2)` | 裂痕一多，火先暗下去 |
| 熄灭时散去的粒子数 | `round(损失魂火 ÷ 5)`，封顶 60 | 失去多少，看得见多少 |
| 熄灭后余烬数 | `clamp(round(已结算魂火 ÷ 20), 1, 12)` | **余烬 = 保留下来的东西**，最少也留 1 粒 |
| 重燃终点亮度 | `实际追回 ÷ 损失` | 追回 40% → 火只回到 40%，**不会假装满血** |
| 重燃三段亮度 | `0.1 → 0.5×终点 → 终点` | 三段对应"余烬→微光→火焰" |

**最关键的一条：重燃的火焰不会恢复到满。** 追回 40% 就只亮 40%。这是这套规则里唯一能让用户"看见规则"的地方——如果失败后火焰还能回到 100%，前面所有关于代价的设计都会变成空话。

## 9. 防自欺：让奖励可信

一个自律 App 的奖惩如果可以被自己糊弄，它就一定会被糊弄。三条最低限度的设计：

1. **完成后必须填实际值**。填了 25 分钟才给 25 分钟的魂火；只点"完成"不填值 → 只记 XP 的 50%，不给魂火。
2. **低于设定值 60% 记"部分完成"**：给 50% 魂火，不给 XP 折扣（避免用户为了 XP 硬凑）。
3. **同一任务同一天只能完成一次**。重复打卡不产生资源。

这三条不做，前面所有关于"损失是真实的"的说法都站不住。

## 10. 三个完整算例

### 例 1 · 深渊，达标结算

```
5 天 × 3 项中任务 = 15 项，魂火池 150，XP 池 600
执行：第 3 天缺 1 项，24h 内补做，裂痕清除
末态：完成率 100% → 结算 150 魂火
篝火：SETTLING 6s（深渊 8s），粒子 30 个
结果：已结算 150 · 永久 XP 600 · 完成徽章（金）
```

### 例 2 · 深渊，F2 熄灭 + 部分恢复

```
同上，第 3/4/5 天各缺 1 项且均未补做 → 裂痕 3
已得魂火 = 12 × 10 = 120
第 5 天日切：F2 触发 → EXTINGUISHING 3.2s
损失 120，可追回 round5(120×40%) = 50，N = 2，每项 25
用户完成 2 项 → 追回 50（进入已结算）
熄灭后余烬数 = clamp(round(50 ÷ 20),1,12) = 3 粒
重燃终点亮度 = 50 ÷ 120 = 0.42
结果：失落 70 · 已结算 50 · XP 480（12 项×40）全额保留
```

### 例 3 · 骑士，未达门槛

```
7 天 × 3 项中任务 = 21 项，魂火池 210
完成 17 项（81%），4 项未完成 → 裂痕 4，未超容忍上限（4）→ 不熄火
阶段末：81% < 85% → 损失 30%
已得魂火 170 → 损失 round5(170×30%) = 50
可追回 round5(50×50%) = 25，N = clamp(ceil(25/25),1,4) = 1，完成 → 追回 25
结果：失落 25 · 已结算 145 · 徽章（81% ≥70%，铜）
```

## 11. 需要你拍板的六个数值

这几个改动会连带影响规则结构，不是调参：

| # | 参数 | 我的建议 | 如果改，连带要改什么 |
|---|---|---|---|
| 1 | **深渊损失比例** | 100% | 改为部分损失 → 深渊与骑士的差异塌陷，需要另找差异点 |
| 2 | **深渊结算门槛** | 100% | 改为 90% → 裂痕机制失去意义，可直接删掉 |
| 3 | **骑士损失比例** | 30% | 影响骑士与旅者的区分度；>50% 会让骑士变成"小深渊" |
| 4 | **追回比例** | 深渊 40% / 骑士 50% | 决定失败后的情绪走向：太高 → 惩罚不成立；太低 → 恢复挑战没人用 |
| 5 | **裂痕上限** | 深渊 2 / 骑士 4 | 直接决定"一轮能容错几天"，是最影响体感的一个数 |
| 6 | **深渊是否允许计划调整** | 0 次 | 允许 1 次 → 深渊变温和，但入场流失会下降 |

### 这些数为什么是这些数

- **100 / 30 / 0** 三档不是等差，是三种不同的心理结构：全有全无、有折扣、无惩罚。等差（100/70/40）会让三个模式读起来像同一件事的三个难度。
- **40% 追回**：低于 30% 用户不会去做（投入产出比太差）；高于 50% 惩罚就不痛了。40% 是"值得做，但补不回来"的位置。
- **裂痕上限深渊 2**：5 天的轮次里，2 次容错 = 40% 的天数可以出问题但不致命。3 次就说明这不是意外，是状态问题。
- **补做窗口 24h**：跨一个完整睡眠周期，覆盖"晚上没做、第二天补"的真实场景，又不至于拖到"这周随便挑一天补"。

## 12. 怎么验证

原文档 §20.2 的态度是对的：这些数是提案，不是结论。建议按三个问题验证，而不是问"你喜欢吗"：

1. **理解度**：给用户看深渊的风险确认页，问"如果我第 3 天没做完，会发生什么"——答不对说明规则没讲清，不是用户笨。
2. **接受度**：让用户在骑士和深渊之间选，观察选深渊的比例与理由。若多数人因为"反正可以恢复"而选深渊，说明 40% 太宽松。
3. **行为验证**：统计失败后 48 小时内发起恢复挑战的比例。低于 30% → 恢复机制设计失败（不是用户懒）。高于 70% 且完成率高 → 惩罚可能不够真实。

**最重要的一个观察指标：失败后 7 天内是否还有行动记录。** 这个数比任何"满意度评分"都更能说明奖惩机制是否成立——它检验的正是原文档 §21 那句"你只需要决定，是否还愿意向前"。
