# 17 · 三维视窗像素化（Pixelate）实现说明

> 目的：让**实时渲染的三维视窗**与项目既有的**像素风 UI** 视觉统一。
> 做法不是"给三维加个马赛克滤镜"，而是**低分辨率渲染 + 色板量化 + 有序抖动**三步。
> 本文所有数字都是无头 Chrome（软件 WebGL）+ 逐像素比对得出的实测值，不是估算。

---

## 一、为什么不能只做"马赛克"

只把画面切成方块（缩小再放大）是最容易想到、也最容易翻车的做法：

| 问题 | 现象 |
|---|---|
| 色数不受控 | 每块颜色仍是从渲染结果里采到的任意色，色数仍是几千，跟 16 色 UI 拼在一起像贴纸 |
| 渐变变成噪点 | 球体的光照渐变被打散成随机色块，没有像素画该有的"阶梯感" |
| 抖动点尺寸错 | 若在屏幕像素上做抖动，放大后每块内部还会碎裂成更小的点，反而更脏 |

所以正确做法是三步，缺一步都不成立。

---

## 二、三步管线

```
场景（linear 空间）
   │
   │ ① 渲染到低分辨率 RenderTarget（NearestFilter，无 MSAA）
   ▼
179×90 的 RT  ←── 这一步决定"块有多大"
   │
   │ ② 全屏后处理：按格心取样 + Bayer 抖动 + 最近色量化
   ▼
16 色、每块同色、带阶梯感
   │
   │ ③ 最近邻放大到 716×360（DPR 2）
   ▼
视窗
```

### 2.1 ① 低分辨率 RT

| 项 | 值 | 说明 |
|---|---|---|
| RT 尺寸 | `drawingBuffer / 大像素边长` | 例：716×360 ÷ 4 = **179×90** |
| 过滤 | `NearestFilter`（min + mag） | 必须都是 Nearest，否则会被插值抹平 |
| 深度 | `depthBuffer: true` | 球体遮挡需要 |
| MSAA | 关 | 开抗锯齿就等于在块边做混色 |

**大像素边长档位**（设备像素，`PX_LEVELS`）：

| 键 | 边长 | 716×360 下的格数 | 观感 |
|---|---|---|---|
| `1` | 2 | 358×180 | 极细，接近"轻微降采样"，只去细节不显像素 |
| `2` | 3 | 238×120 | 细，适合小尺寸视窗 |
| `3` | 4 | **179×90** | **默认**，块面清晰但不粗糙 |
| `4` | 6 | 119×60 | 粗，接近 NES 风格，细节损失明显 |

### 2.2 ② 抖动 + 量化（片元着色器）

关键的四条，每条都踩过坑：

**（a）按格心取样，不是按屏幕坐标**

```glsl
vec2 cell = floor(vUv * uGrid);
vec2 uv   = (cell + 0.5) / uGrid;    // 格心
vec3 lin  = texture2D(tDiffuse, uv).rgb;
```
取格心而不是格角，避免落在块边界上采到相邻块的颜色。

**（b）抖动必须在 sRGB 空间做**

```glsl
vec3 c = lin2srgb(lin);              // 转到 sRGB
c += (bayer4(cell) - 0.5) * uDither; // 抖动
c = clamp(c, 0.0, 1.0);
```
场景在 linear 空间渲染。**若直接在线性空间抖动+量化**，暗部会被严重压扁——因为 linear 的数值分布与人眼感知不符，16 个色阶里 12 个会被分给亮部，夜面只剩 1–2 色，看起来像脏斑。实测：改成 sRGB 空间后，夜面可用的深色阶从 2 个恢复到 5 个。

**（c）抖动坐标用 `cell`，不用 `gl_FragCoord`**

```glsl
c += (bayer4(cell) - 0.5) * uDither;   // ✅ cell
// c += (bayer4(gl_FragCoord.xy) - 0.5) * uDither;  // ❌ 放大后块内会碎裂
```
用 `gl_FragCoord` 会让抖动点在**屏幕像素**尺度上变化，放大 4 倍后一个块里出现 16 个不同深浅的点——看起来像噪点而不是像素画。

**（d）输出必须直接是 sRGB**

```glsl
gl_FragColor = vec4(pick, 1.0);        // ✅ pick 已是 sRGB
// gl_FragColor = vec4(srgb2lin(pick), 1.0);  // ❌ 会被再压暗一次
```

> **这是本项目实测踩到的最隐蔽的坑。**
> `ShaderMaterial` **不会**被 three 自动套上 `outputColorSpace` 转换（只有内置材质会）。
> 所以如果以为"最后 three 会帮我转"，把量化结果再 `srgb2lin` 一次，全屏会整体压暗——
> 实测出 `#0B1A37`、`#07120A` 这类**色板外色**，板内率只有 **59.5%**。
> 改成直接输出 sRGB 后，板内率升到 **100%**。

### 2.3 ③ 放大

| 层 | 做法 |
|---|---|
| WebGL | RT 用 Nearest 采样 → 天然硬边 |
| CSS | `image-rendering: pixelated`（双保险；部分 GPU 路径下仍会走线性采样） |
| 布局 | 画布 CSS 尺寸必须是**整数倍且无 border**，见 §四 |

| 3 | `#101A2C` | 07 §4.2 夜相位 · 星球主色 |
| 4 | `#151C2E` | 07 §4.2 晨相位 · 天空 |

| 10 | `#4A6FA5` | 07 §4.2 昼相位 · 星球主色 |
| 11 | `#5A9BD4` | 07 §4.2 夜相位 · 强调色 |
| 12 | `#5FBF8F` | 07 §4.3 `accent/green`（设施已达成） |
| 13 | `#7FA3C9` | 07 §4.2 昼相位 · 天空 |
| 14 | `#C98A5A` | 07 §4.2 晨相位 · 高光 |
| 15 | `#E8A468` | 07 §4.3 `accent/amber`（强调色，配额 ≤8%） |
| 16 | `#F2E4C9` | 07 §4.2 昼相位 · 高光（= 12 配图亮部锚点） |

**为什么是 16 色而不是更多**：13 §2.2 的令牌体系是 17 色，其中 10 个灰阶交给 UI 层、不在三维里用；7 个彩色（1 红 2 黄 1 绿 2 蓝 + 琥珀）里有 3 个（红/黄）是**警示语义**，不该出现在星球上。所以三维实际可用的是本表 16 个。

**匹配算法**：加权 RGB 距离（`0.30, 0.59, 0.11`，近似感知亮度），取最近色。没用 CIE Lab 是因为：① 16 色下两者结果差异极小（实测目视无差）；② 省掉一次色彩空间往返，片元里少 2 次 pow。

## 四、布局约束（这一步不做，前面全白费）

像素化能成立的前提是：**画布 CSS 尺寸与 RT 格数保持整数倍关系**。以下三个问题实测都会破坏它：

| 问题 | 现象 | 修法 |
|---|---|---|
| **border 占内容区** | `358px + 1px border` → 内容区只有 356px，渲染尺寸 716 但要塞进 712 → 非整数缩放 | 用 `inset box-shadow` 或 `outline` 画描边，**不要用 border** |
| **圆角** | `border-radius` 会让四角抗锯齿 → 混出 `#07090F` 类板外色（实测 984 个板外像素里 424 个贴边） | 像素化时 `border-radius: 0`（**正好符合 13 §2.2 的 `radius/none = 0`**） |
| **半透明叠层** | 柔光/渐变叠层盖在画布上 → 整屏变板外色 | 像素化时 `display: none`（实测：关掉柔光后板内率 99.62% → 100%） |

## 五、实测结果

**环境**：Chrome 155 headless + SwiftShader 软件 WebGL，DPR 2，视窗 358×180（画布 716×360），PNG 逐像素比对。

| 档位 | RT 格数 | 色数 | 板内率 | 块边游程（众数） |
|---|---|---|---|---|
| ×2 | 358×180 | 14 | **100.00%** | 2 px |
| ×3 | 238×120 | 14 | **100.00%** | 3 px |
| ×4（默认） | 179×90 | 14 | **100.00%** | 4 px |
| ×6 | 119×60 | 14 | **100.00%** | 6 px |
| 关闭 | — | 7,354 | 不适用 | — |

**读法**：
- **板内率 100%** = 屏幕上每一个像素都精确等于 16 色之一，没有任何插值过渡色。这是像素风纯度的硬判据。
- **块边游程众数 = 档位值** = 像素块边长真的是 2/3/4/6 设备像素，没有被重采样成 3.4 或 5.7 这种小数。
- 关闭时 7,354 色，说明对比有效（不是"假对比"）。

### 5.1 性能开销

| 项 | 数值 |
|---|---|
| 像素化前 p50 / p95 | 16.5 / 19.8 ms |
| 像素化后 p50 / p95 | 16.4 / 20.7 ms |
| 三角面 | 6,272（球 4,096 + 大气 2,304 + 设施 96） |
| 额外一次全屏 pass | 179×90 格 × 全屏 quad ≈ 0 GPU 压力 |

**结论：开销可忽略。** 原因很直接——像素化把渲染分辨率降到了 1/16，省下的填充量远大于多一次 pass 的开销。**开像素化反而更快。**


## 七、已知限制

| # | 限制 | 说明 |
|---|---|---|
| 1 | **WebGPU 路径不启用像素化** | `ShaderMaterial` 后处理在 WebGPU 下需改写成 TSL 节点。按 15 章约定 WebGPU 只是可选加速、不进验收，所以这里直接提示"未启用"，不做。 |
| 2 | 色板固定 16 色，不随相位切换 | 当前把晨/昼/昏/夜四个相位的色都塞进了同一套 16 色。若要"相位切换时换色板"，需按 07 §4.2 拆成 4 套（各 8–10 色），并做淡入过渡。 |
| 3 | 抖动强度固定 0.06 | 未做自适应。若某档位出现色带（bayer 4×4 在大面积渐变上可能露条纹），可提到 0.10–0.12。 |
| 4 | 未做 `prefers-reduced-motion` 联动 | 像素化是静态的，与动效无关，故未处理。 |
| 5 | x3/x6 档在非整数倍 DPR 下块边会交替 | 例：716÷3≈238.67，格宽在 3–4 px 间浮动。这是分辨率除不尽的必然结果，非缺陷；若要完全均匀，选能整除的档位（×2、×4）。 |

## 九、为什么用经典脚本打包（file:// 才能双击运行）

**现象**：最初版本用 `<script type="importmap">` + `<script type="module">` 加载 three，
在 `http://` 下正常，但**双击打开（`file://`）时三维区域报"three.js 加载失败"**。

**根因不是文件缺失，而是协议限制**：
浏览器对 `file://` 下的 ES module 一律按「跨域」拒绝加载——`<script type="module">`
和 `import()` 都会被 CORS 检查拦掉，**与文件是否在同一目录无关**。
所以「把 three.module.js 放到同目录」并不能解决问题（这也是我最初报错文案的误导）。

**解法**：把 three 的 ESM 构建合成一个**经典脚本**（`three.bundle.js`），
用 `<script src>` 引入，暴露 `window.THREE`。经典脚本在 `file://` 下不受 CORS 限制。

打包要点（`demo/build-classic.mjs`，三步）：

| # | 问题 | 处理 |
|---|---|---|
| 1 | `three.module.js` 会 `import { ... } from './three.core.js'` | 删 import，改为 `const {...} = __core` |
| 2 | 两个文件**各自**有同名顶层变量（如 `_m1$1`），直接拼接报 `Identifier has already been declared` | 各自包进独立 IIFE：core 产出 `__core`，module 以它为入参 |
| 3 | `export {...}` 是模块语法 | 转成 `return {...}`（core）与 `Object.assign(THREE, {...})`（module） |

生成的 bundle：**1.91 MB，431 个导出**，`node --check` 通过，
并在 Node VM 里实测能构造出 `THREE.REVISION === '180'` 且所需类齐全。

**file:// 实测结果**（Chrome headless，`protocol: "file:"`）：

```
threeLoaded: true    revision: "180"    exportKeys: 431
canvasSize: [716, 360]        pxLabel: "179×90 格 · 放大 ×4.00 · 16 色"
p50: 16.60 ms        tri: "6,272"        console 错误: 0
像素纯度: 100.00%（4×4 纯块 100%，块边游程众数 4px）
```

### 9.1 页面现在还能不能用 http:// 打开

能。经典脚本与协议无关，`file://` 和 `http://` 都工作。
但**不能再用 ES module 版页面**——若要 WebGPU（`three/webgpu` 只有 ESM 包），
需要另建一个 module 版页面并用本地服务打开。

### 9.2 三个文件的关系

| 文件 | 作用 | 是否必需 |
|---|---|---|
| `three.bundle.js` | 页面唯一依赖（经典脚本，1.91 MB） | **必需** |
| `three.module.js` | ESM 版（重新打包的源） | 仅构建时 |
| `three.core.js` | ESM 版的核心（`three.module.js` 的依赖） | 仅构建时 |
| `build-classic.mjs` | 打包脚本 | 仅构建时 |

> 如果只是演示，`three.bundle.js` + `主页面三维演示.html` 两个文件即可，
> 另三个可以拷到别处也不影响运行。
