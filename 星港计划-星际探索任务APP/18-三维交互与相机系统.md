## 一、要解决什么

上一版三维区是"永远匀速自转的装饰动画"：球一直在转，用户除了按 `V` 切换两个固定机位，
什么都做不了。这一版要把它做成**能操作的地图**：

| 需求 | 实现 |
|---|---|
| 别一直转 | 待机才转，且降到 0.083 rad/s（约 76 秒一圈） |
| 待机时全景低速度自转 | `globe` 模式 + 2 秒无操作后启动 |
| 拖动旋转 | 单指横向拖动 → 绕竖轴转；纵向拖动 → 改俯角 |
| 点击地表建筑物聚焦 | 射线拾取 → 1350ms 螺旋飞行到地平线视角 |
| 切换到地平线视图 | `focus` 模式：天空 ≈1/3、建筑在下三分之一 |
| 移动端双指缩放 | 双指捏合改相机距离 |

**核心设计取舍**：相机只有两种模式（`globe` / `focus`）加一个过渡态（`transit`），
不是一个自由度很高的自由相机。原因是课设范围里"自由相机 + 防穿模 + 边界约束"会让调试成本翻倍，
而两个模式已经能覆盖"看全局"和"看一处"这两种真实场景。

## 二、状态机

```
        ┌──────────────────────────────────────┐
        │                                      │
        ▼                                      │
   ┌─────────┐   点建筑（射线命中）    ┌──────────┐
   │  globe  │ ──────────────────────▶ │  focus   │
   │ 全景待机 │                         │ 聚焦一处  │
   └─────────┘ ◀────────────────────── └──────────┘
        ▲         点空白 / Esc                │
        │                                     │
        └──────── transit (1350ms) ───────────┘
                    过渡期间不接受输入
```

`transit` 期间四条时间线**重叠推进**（见 §2.3）：

```
e(x)  = cubic-bezier(.42, 0, .58, 1)          // 三次贝塞尔缓动
pos   = Bezier3(from.pos → 螺旋控制点 → to.pos)  按弧长取参
look  = lerp(from.look, to.look, e)
dist  = lerp(from.dist, to.dist, e)           // 驱动 LOD 缩放
up    = lerp(from.up,  to.up,  e)             // 地平线摆正
```

用 lerp 位置 + 看点而不是 lerp 欧拉角，是因为两模式相机朝向差得太多（一个是绕球看、
一个是贴着地表看），角度插值会在中途穿过奇怪姿态。

### 2.1 缓动：三代曲线，峰值一路降下来

| 代 | 曲线 | 峰值速度 / 平均速度 | 备注 |
|---|---|---|---|
| 一 | cubic ease-in-out | **3.000** | 二阶导在 t=0.5 由 +12 突变为 −12 |
| 二 | quintic smootherstep | **1.875** | 二阶导全程连续 |
| 三（当前） | **三次贝塞尔** `cubic-bezier(.42,0,.58,1)` | **1.724** | 曲线里峰值最低的一档 |

三次贝塞尔用 CSS 那套算法实现（牛顿迭代解 x→t，失败则二分兜底）：

```js
function cubicBezierEase(x1, y1, x2, y2) { … }
const EASE_POS  = cubicBezierEase(0.42, 0.00, 0.58, 1.00);
const EASE_LOOK = cubicBezierEase(0.50, 0.00, 0.45, 1.00);
```

**反直觉的一点**：把两端压得更慢并不会更柔，反而更冲 ——
两端压得越死，中段就被逼得越快：

| 曲线 | 峰值/平均 |
|---|---|
| `cubic-bezier(.42, 0, .58, 1)` | **1.724** |
| `cubic-bezier(.50, 0, .50, 1)` | 2.000 |
| `cubic-bezier(.60, 0, .40, 1)` | 2.500 |
| `cubic-bezier(.65, 0, .35, 1)` | 2.857 |

所以"缓入缓出"不是越强越好。1.724 是这一族里较好的一档。

### 2.2 三个让动画"变冲"的陷阱（都是实测抓出来的）

这一轮把峰值速度从 **6.1 R/s 压到 3.4–4.2 R/s**，靠的不是换缓动，
而是修掉三个把缓动曲线拧坏的地方：

| # | 陷阱 | 现象 | 修法 |
|---|---|---|---|
| 1 | **贝塞尔按参数 t 采样** | 参数速度天然中段快两端慢，把缓动压出的剖面再拧一次：峰值/平均 1.72 → **2.59** | 建累积弧长表，用弧长比例反查 t（弧长重参数化） |
| 2 | **缓动被压进子窗口** | 速度整体乘以 1/窗口宽度；位置放在 `[0, 0.86]` 时 1.724 ÷ 0.86 = **2.005** | 位置窗口吃满 `[0, 1]`，其余三条错开让位 |
| 3 | **终点每帧重算** | `S.dist` 从 3.6 动画到 1.10，终点跟着往里跑，等于追移动靶，又把剖面拧一次（实测 2.05） | 路径在过渡开始时定死（控制点 + 弧长表只建一次） |

修完之后实测**平滑后**峰值/平均：最近建筑 1.714、最远建筑 1.689（理论 1.724）。

### 2.3 重叠时间窗

过渡不是"一个动作演完再演下一个"，而是几条时间线错开叠在一起：

```
位置 ████████████████████     0.00–1.00   主飞行（吃满整条时间线）
距离 ░███████████████░░░░     0.04–0.80   较早完成 → LOD 缩放先收住
up   ░████████████░░░░░░░     0.02–0.62   更早完成 → 地平线途中就摆正
看点 ░░░█████████████████     0.10–0.98   起步最晚 → 先飞、后瞄
```

窗口重叠的部分就是"同时进行"。实测**角位移与半径变化的显著区间重叠 58%** ——
即"绕过去"与"降下去"是一个连续动作，不是先对正再过渡。

这正是原先"像是先对正、再过渡"的根因：旧代码里 `planet.rotation.y = S.spin`
写在 `if (S.mode === 'globe')` 内部，一点建筑星球就**当帧定死**。
现在自转强度走一条 0→1 的斜坡（`idleRamp`），星球带着惯性缓缓减速，
与相机的飞行同时进行。

## 三、globe 全景机位

球面轨道相机，位置由**距离 + 俯角**决定，绕球心：

```js
camera.position = (0, sin(el)·d, cos(el)·d)
camera.lookAt(0, 0, 0)
camera.up = (0, 1, 0)
```

### 3.1 默认距离为什么是 3.6R

视口 390×227，`aspect = 1.72`。球的投影尺寸**受高度约束**（不是宽度）：

| d | 球角直径 | 占屏高 | 结论 |
|---|---|---|---|
| 2.3 | 51.5° | 153% | 裁太多，看不出是球 |
| 3.0 | 38.9° | 112% | 上下略裁 |
| **3.6** | **32.3°** | **92%** | **完整可见且够大** |
| 4.2 | 27.5° | 78% | 偏小 |
| 5.0 | 23.1° | 65% | 太小 |

取 3.6：完整、接近满高、留一点余量给自转时的视觉呼吸。

### 3.2 参数范围

| 项 | 值 |
|---|---|
| 距离 | 2.80 – 5.60 R，默认 3.60 |
| 俯角 | 4° – 58°，默认 18° |
| 待机自转 | 0.055 rad/s ≈ 76 s 一圈 |
| 惯性衰减 | 每帧 ×0.92 |

### 3.3 顶部安全区：星球必须让开 47px

三维画布是**无界满幅**的，状态栏（39px + 上边距 8px = **47px**）浮在它上面。
如果星球按容器居中，顶端会跑到 y=5.4 —— 整条上沿被状态栏压住。

做法：在 `globeTargets()` 里把**视线往上抬一个角 α**，星球在画面上就相应下移。
α 取两段约束的较大者：

| 约束 | 条件 | 公式 |
|---|---|---|
| ① 顶端 | 把星球（含 1.035R 大气壳）的**上切线**压到安全线下 | `α₁ = angR − atan((1 − 2·SAFE_TOP/H) · tan(halfFov))` |
| ② 居中 | 星球比可用区小时别贴顶，在 `[SAFE_TOP, H]` 里居中 | `α₂ = atan((bandCenter − H/2)/(H/2) · tan(halfFov))` |

其中 `angR = asin(ATM_R / d)` 是星球的角半径。

**为什么用"抬视线"而不是改投影矩阵/镜头位移**：改投影会同时改变 FOV 语义，
而聚焦视角的取景是逐像素实测校正过的，不能被动到。抬视线只影响全景。

实测（7 个缩放档位，像素实测 vs 面板预测）：

| dist | 抬升 α | 星球顶端 y | 面板 | 底端 y |
|---|---|---|---|---|
| 2.8 | 11.2° | 48.0 | 47 | 226（溢出） |
| 3.0 | 9.7° | 48.0 | 47 | 226（溢出） |
| **3.6（默认）** | **6.2°** | **48.0** | **47** | **226（溢出）** |
| 4.0 | 4.5° | 48.0 | 47 | 222（溢出） |
| 4.5 | 3.7° | 54.0 | 53 | 222 |
| 5.0 | 3.7° | 63.0 | 62 | 213 |
| 5.6 | 3.7° | 70.5 | 70 | 204 |

全部档位顶端 ≥ 47 ✓，实测与面板差 ≤1px。

> **量这个数要小心测量窗口**。第一版直接全宽扫描「连续非天空像素」，结果
> ① 第 0 行就有 73 连段 —— 那是**手机框圆角**（`#phone` 的 `border-radius:38px`）裁掉的画布顶角；
> ② 后面几档又被**标题文字**（y 47–85）和**右上圆图标**（CSS `top:59px`，逻辑 x 294–374）抢先命中。
> 最后把窗口收到**逻辑 x 200–288**（避开标题与图标）才测准。
> 判据用「该行有 ≥20 连续非天空像素」——球顶是连续实心，星点是孤立 1–2px，不会误判。

底部裁切是必然的：可用高度只有 180px，而默认距离下星球投影高 219px。
视觉上像"星球从下边缘升起"，与地平线视角同一套观感。
若不想裁切，把默认距离放到 4.5（星球高 171px，正好落在 53–224）。

调试面板新增一行 `星球 y 范围`，直接显示 `顶端 – 底端 px（抬 N°）`，
顶端低于安全线时标绿，方便随时核对。

## 四、focus 聚焦机位：以建筑为球心的第二层轨道相机

相机不是钉在一条固定射线上，而是**绕建筑旋转**。步骤：

```js
// ① 建筑处的局部正交基
n  = 该点法线（也是球的径向）
tN = (-sin(lat)·sin(lon), cos(lat), -sin(lat)·cos(lon))   // 朝北切向
tE = n × tN                                                // 朝东

// ② 先算出实测验证过的 home 机位，再换成「相对建筑的偏移」
home = normalize(n − back·tN) · FAC.dist
off  = home − P                     // P = n · FOC_PIVOT_R

// ③ 把 off 在局部基下分解成球坐标 (r, θ₀, φ₀)
r  = |off|
θ₀ = acos( off·n / r )
φ₀ = atan2( off·tE, off·tN )

// ④ 叠加用户拖动量，并夹住极角（见 4.4）
θ = clamp(θ₀ + fPol, 22°, θmax)
φ = φ₀ + fAz

// ⑤ 还原成方向
pos = P + r'·( n·cosθ + (tN·cosφ + tE·sinφ)·sinθ )
      r' = r · S.dist / FAC.dist        // 缩放仍走 S.dist，沿用既有范围

// ⑥ 看向建筑，再绕 right 抬 pitch（把建筑压到画面下三分之一）
dir   = normalize(P − pos)
right = normalize(cross(dir, n))
dir.applyAxisAngle(right, pitch)
look = pos + dir
```

**关键性质**：`fAz = fPol = 0` 时 `pos = P + off = home`、`look = P`，
与原 home 机位**数学上完全相同**，所以 §4.1 那套实测校正过的取景被原样保留
（实测复核：建筑仍在 x=50.0%、y=68.2%，天空仍 35.9%）。

### 4.1 取景参数（实测校正过）

| 参数 | 值 |
|---|---|
| `dist` | **1.10 R** |
| `back` | **0.19 R** |
| `pitch` | **+8°** |
| 缩放范围 | 1.03 – 1.80 R |

**实测结果**（780×454 截图逐像素统计）：

| dist | 天空占比 | 建筑屏位置 y | 建筑色像素数 |
|---|---|---|---|
| 1.05 | 41.0% | 67.5% | 200 |
| **1.10** | **35.9%** | **68.2%** | **1908** |
| 1.15 | 28.4% | 68.9% | 3560 |
| 1.20 | 22.3% | 69.6% | 3695 |
| 1.30 | 14.7% | 70.5% | 4326 |

取 1.10：天空 35.9%（≈1/3），建筑在屏幕 68% 处、可点面积约 1900 像素。

> **枢轴半径为什么取 1.0 而不是设施的 1.006**
> 原 home 机位的 lookAt 就是单位法线方向（半径 1.0）。若把枢轴和看点改成设施网格的
> 1.006，"相机→看点"的仰角会从 21.45° 变成 19.99°，叠上 +8° pitch 后
> 建筑屏位从 68.2% 掉到 **72.3%** —— 实测确实漂了 4%，已改回 1.0。
> 设施盒体实际跨半径 0.986–1.026，1.0 就落在盒体内部，取作枢轴没有问题。

> **为什么不用解析公式直接解**
> 一开始按「天空面积 = 1/3」对半径 1 的球做逐像素求交反解，得到 `dist = 1.20`、
> 预测天空 33.4%。实际渲染出来只有 22.3%。
> 差在**大气壳**：场景里还有一层 `1.035R` 的透明球，它把地平线上方一条天空也盖住了。
> 相机越贴近地表，这层壳占的视角越大，误差越明显。
> 所以解析值只能用来定位区间，最终参数必须按实际渲染帧实测。

### 4.2 `camera.up` 必须换成径向

这一条是**最容易错**的地方：

`camera.lookAt()` 默认用 `up = (0,1,0)`。但 focus 模式下相机贴着 latitude 44–64° 的地表，
该点的径向与该纬度相差 26–46°，用世界 +Y 当地平线会**把地平线转斜**。

实测截图里地平线明显左高右低（中央区高低差 40px / 8.8%）。
换成 `camera.up = 该点径向 n` 之后，地平线才是水平的（中央区高低差降到 26px / 5.7%，
剩下的量是球面本身的曲率，不是倾斜）。

```js
if (S.mode === 'focus')       camUp.lerp(worldNormalOf(S.focusIdx), k);
else if (S.mode === 'transit') camUp.lerp(S.next === 'focus' ? n : WORLD_UP, k * 0.6);
else                           camUp.lerp(WORLD_UP, _followK(20, dtSec));
camera.up.copy(camUp.normalize());
```

（`k` 是跟手系数，见 4.6。）

### 4.3 建筑要做距离补偿缩放（LOD）

建筑世界尺寸 0.028×0.040×0.028 R。透视下屏高 ∝ 1/相机到建筑距离：

| 模式 | 相机到建筑距离 | 建筑屏高 |
|---|---|---|
| focus | ≈0.27 R | ≈55 px |
| globe | ≈2.6 R | ≈4.6 px（看不清也点不准） |

所以按距离反向放大：

```js
const lvScale = clamp((S.dist - 0.95) / 1.4, 1, 3.2);
facs.forEach(m => m.scale.setScalar(lvScale));
```

物理上不正确，但交互上必要——这是游戏里常见的 LOD 手法。

### 4.4 极角夹取（两个约束都要满足）

绕建筑转时 θ 不能无限变，否则会出事：

| 约束 | 说明 | 处理 |
|---|---|---|
| 相机不能钻进大气壳 | 相机半径 ≥ 1.05 R（大气壳 1.035 R） | 按当前 r 反解 θ 上限 |
| `lookAt` 不能退化 | 相机方向与 `up`（= 径向 n）接近共线时 lookAt 会翻 | θ 下限 22° |

θ 上限是**动态**的，因为缩放会改变 r：

```js
const cosLim = (FOC_R_MIN² − FOC_PIVOT_R² − r²) / (2·FOC_PIVOT_R·r);
const thMax  = max(22°, acos(clamp(cosLim, −1, 1)));
```

| 缩放 | r | θ 上限 | 实测相机半径 |
|---|---|---|---|
| 最近 1.03 | 0.205 | 83.0° | 1.0500 R ✓ |
| home 1.10 | 0.219 | 83.0° | 1.0998 R |
| 最远 1.80 | 0.357 | 88°（触到硬上限） | — |

**反算防累积**：夹取后把结果写回 `S.fPol = θ − θ₀`。
若不写回，用户拖过头之后反向拖要先把"虚拟超出的量"拖回来，手感是"粘住"。
实测：在 θ=22.00° 处超拖 6 次后，反向拖 40px 立刻变到 31.17°（Δ=9.17°，与理论值完全一致）。

### 4.5 飞行路径：贴着球面的螺旋

直线插值的问题：从 3.6R 直插 1.1R 走的是弦，观感是"缩进去"而不是"飞过去"。

我第一版用"控制点朝远离球心方向外鼓"的贝塞尔，结果**几乎没变形** ——
因为从 3.6R 降到 1.1R 时，"远离球心"的方向与航线方向几乎平行
（实测夹角 155°，即 91% 重合），往外鼓等于沿航线推。
实测偏离只有 2.4% 弦长，而理论上该有 12%。

改成**螺旋**：方向走 `slerp`（沿大圆绕过去），半径线性插值 + 中段轻微抬升，
再把螺旋上 1/3、2/3 的点取作三次贝塞尔的控制点（曲线因此贴着螺旋走）。

```js
function spiralPoint(out, p0, p1, t, lift = FLY_LIFT) {
  const r0 = p0.length(), r1 = p1.length();
  slerpDir(_sp, p0.clone().divideScalar(r0), p1.clone().divideScalar(r1), t);
  const r = r0 + (r1 - r0) * t + lift * p0.distanceTo(p1) * Math.sin(Math.PI * t);
  return out.copy(_sp).multiplyScalar(r);
}
```

实测两种极端情形：

| 目标建筑 | 与相机角距 | 路径长/弦长 | 偏离弦（朝外） | 最小半径 |
|---|---|---|---|---|
| 最近 #0 | 23.6° | 1.016 | 7.7% 弦长 | 1.1001 R |
| 最远 #5 | 54.4° | 1.058 | 14.9% 弦长 | 1.1005 R |

`FLY_LIFT` 只是 0.05 —— 抬得越高路径越长、平均速度越快，反而更"冲"。

**弧长重参数化**（对应 §2.2 陷阱 1）：

```js
const tPos = tAtArcLen(_ease(_win(t, ...WIN_POS)), S.arcTotal);
bezier3(camPos, S.from.pos, S.c1, S.c2, S.to.pos, tPos);
```

24 段的累积弧长表在过渡开始时建一次，之后每帧只做一次二分查表。

## 五、输入处理

### 5.1 只用 Pointer Events

不用 `touchstart/touchmove` + `mousedown/mousemove` 两套。`pointerdown/move/up/cancel`
一套同时覆盖鼠标、触摸、手写笔，`pointerId` 用来区分多指。

```js
T.pointers = new Map()   // pointerId → {x, y}
```

| 事件 | 处理 |
|---|---|
| `pointerdown` | 记入 Map；单指时启动拖动并做一次射线拾取；双指时记录初始间距 |
| `pointermove` | 双指 → 算间距比改 `S.dist`；单指 → globe 改 `S.spin`/`S.el`，focus 改 `S.fAz`/`S.fPol` |
| `pointerup` | 全部抬起时：**且未拖动过**时，有命中 → 聚焦，在 focus 且未命中 → 退回 |

### 5.2 点击与拖动的区分（这里踩过一个坑）

按下时记 `downPos`，移动超过 **6px** 就置 `T.moved = true` 并把候选命中清成 -1。
抬起时**必须同时满足 `!T.moved`** 才当作点击：

```js
if (wasSingle && !T.moved) {
  if (T.downOn >= 0) goFocus(T.downOn);        // 点中建筑 → 聚焦
  else if (S.mode === 'focus') goGlobe();      // 点空白 → 退出聚焦
}
```

第一版只判断了 `T.downOn === -1`，没判断"是否拖动过"。
后果：**聚焦态下随便拖一下、一松手就被踢回全景**（拖动会把 `downOn` 清成 -1，
正好命中"点空白"的分支）。实测表现为 `mode focus → globe`，已修。
现在拖动只是环绕，只有真正的轻点空白才退回。

### 5.3 拾取要用两层

```js
raycaster.intersectObjects(facs, false)   // ① 精确射线
// ② 兜底：屏幕空间最近距离 < 20px 也算命中
```

只靠射线不够：建筑在 globe 下屏幕尺寸只有几个像素，`BoxGeometry` 的三角面很小，
射线必须精确穿过才算命中，手指根本点不到。屏幕空间兜底把命中区放宽到 20px。

### 5.4 双指缩放

```js
k = 初始间距 / 当前间距      // 张开 → k < 1 → 距离变小 → 拉近
S.dist = clamp(初始距离 * k, min, max)
```

注意用**初始距离 × 比例**而不是累乘当前值，否则会因浮点累积产生漂移。

### 5.5 聚焦态拖动 = 绕建筑环绕

| 方向 | 量 | 系数 | 满屏拖动的效果 |
|---|---|---|---|
| 横向 dx | `S.fAz`（方位角） | **−**×0.008 | 390px ≈ 3.12 rad ≈ 179° |
| 纵向 dy | `S.fPol`（极角） | ×0.004 | 往下拖 = 相机升高 = 更俯视 |

**横向取负号是实机调试后按反馈改的。** 两种手感对应不同的符号：

| 符号 | 手指右移时 | 手感 |
|---|---|---|
| `fAz +=`（旧） | 画面内容右移 | "拖拽物体"——内容跟着手指 |
| **`fAz -=`（当前）** | 画面内容左移 | **"转动视角"——像转头看** |

判定用的不是"看起来对不对"，而是量**远处地标屏幕 x 对 fAz 的斜率**：
实测 **+370 px/rad**（fAz 增大 → 地标右移），所以 `fAz` 减小时地标确凿地往左走。

> ⚠️ **测方向不能用地表近点当参照**。第一版探针取了离枢轴 3° 的地表点，
> 测出的斜率只有 19 px/rad —— 因为该点几乎在旋转轴上，
> 相机绕它转时它的屏幕位置按 `0.052·cos φ` 振荡，而不是扫过。
> 必须用远处的参照物（半径 15 的点或背景星），屏幕位移才直接反映相机转动。

纵向方向与 globe 保持一致：两个模式下"往下拖"都是"相机升高"。

因为 `look` 始终指向枢轴（只加固定 pitch），所以**建筑在任何方位角下都钉在同一屏幕位置**
（实测转 4.48 rad ≈ 257° 后仍是 x=50.0%、y=68.2%），相机↔枢轴半径恒定 0.2185 R
（正圆轨道，实测整圈不变）。

## 七、已知限制

| # | 限制 | 说明 |
|---|---|---|
| 1 | focus 环绕时星球不自转 | 环绕靠移动相机实现，星球保持静止（否则建筑会跑出视锥）。副作用：看不到"建筑自转"的感觉，但这是正确取舍。 |
| 7 | 聚焦态没有"回到 home 机位"的手势 | 退出再进一次才复位。可以补一个双击复位或一个小小的复位按钮。 |
| 8 | 枢轴固定在球面点，不跟随建筑 LOD 缩放 | 建筑在 globe 下被放大 3.2×，聚焦时缩回 1×，视觉上有个跳变。可加过渡。 |
| 2 | 没有点击涟漪 / 高亮反馈 | 选中态只是切换视角，建筑本身没有视觉变化。设计稿阶段应该补一个脉冲光圈。 |
| 3 | 建筑是盒体占位 | 不是 8 种形制族的真实模型（见 05 章）。 |
| 4 | 无惯性拖尾曲线调优 | 惯性只是每帧 ×0.92 的指数衰减，没有做"松手速度 vs 位移"的映射。 |
| 5 | 未做双指旋转 | 只做了缩放。旋转手势（两指绕轴）需要额外算角度差，课设范围没做。 |
| 6 | 未处理多指与页面滚动冲突 | 已加 `touch-action: none`（在 `#stage` 上）；但整个页面若后续改成可滚动，需要重新验证手势归属。 |
| 9 | 过渡期间不接受输入 | 1350ms 里点按会被丢掉。若嫌久，可加"点击打断过渡"或把 `TRANSIT_MS` 调到 900。 |
| 10 | 过渡曲线与窗口是常量 | `EASE_POS` / `WIN_*` / `FLY_LIFT` / `TRANSIT_MS` 都是文件顶部常量，调手感不用改逻辑，但目前没有运行时面板。 |
| 12 | 顶部安全区是硬编码 47px | 对应 `#phone` 的状态栏 39 + 上边距 8。若改这两处 CSS，要同步改 `SAFE_TOP`。标题区实际延伸到 y≈85，但那属于"浮动 UI 压在画面上"的设计意图，没有一并让开。 |
| 11 | 路径只按"起点→终点"生成 | 没有做障碍规避。设施都在同一颗球的表面，两点之间的大圆弧不会穿过球体，所以课设范围内够用；若以后设施会浮空或地下，需要重做。 |

## 八、答辩可讲的点

> "三维视窗不是一段循环动画，是一个有状态的地图。全景可以拖、可以缩放，
> 点地表建筑就飞过去 —— 1350ms，几条时间线重叠着跑：相机沿贴着球面的螺旋飞、
> 星球同时带惯性缓缓停转、地平线在途中就摆正、镜头最后才收。
> 聚焦之后还能绕着建筑转圈，建筑始终钉在同一个屏幕位置。
>
> 过渡曲线换了三代：cubic ease-in-out（峰值 3.00× 平均）→ smootherstep（1.875×）
> → 三次贝塞尔（1.724×）。但真正的收益不在换曲线 ——
> 峰值速度从 6.1 R/s 降到 3.4 R/s，靠的是修掉三个把曲线拧坏的地方：
> ① 贝塞尔按参数采样，速度天然中段快，1.72 被抬到 2.59，要用弧长重参数化；
> ② 缓动被压进 86% 的子窗口，速度整体乘以 1/0.86，1.724 变 2.005，位置得吃满整条线；
> ③ 终点每帧重算等于追移动靶，又把剖面拧一次。
> 三条都是逐帧测速度剖面量出来的，不是'看着不顺眼就加时长'。
>
> 另一个坑是路径形状：我第一版用'控制点朝远离球心外鼓'的贝塞尔，
> 结果几乎没变形 —— 因为从 3.6R 降到 1.1R 时，'远离球心'与航线方向重合 91%，
> 往外鼓等于沿航线推（实测只偏离 2.4% 弦长，理论该有 12%）。
> 改成贴着球面的螺旋，'绕过去'和'降下去'才合成一个动作。
>
> 还有几个是实测才发现的：`lookAt` 默认用世界 Y 当上方向，建筑在中高纬度时
> 地平线会歪 40px，改成用该点径向才正；聚焦取景距离按天空占 1/3 反解出 1.20R，
> 实际渲染只有 22%，查出来是大气壳挡了一部分天空，校正到 1.10R 才得到 35.9%；
> 轨道枢轴一开始用了设施的 1.006，取景漂 4%，改回球面 1.0 才对齐。"

### 附：调试链路不再杀 Chrome

早期脚本用 `Get-Process chrome | Kill` 清场 —— 那会**连用户自己开着的浏览器一起杀掉**，
而且并不必要。现在统一用 [`demo/_cdp.mjs`](../demo/_cdp.mjs)：

| 做法 | 说明 |
|---|---|
| 固定端口 + 固定 `user-data-dir` | 跨次复用同一个 headless 实例，不重复启动 |
| 不存在才启动，且 `detached` | 脚本退出不会带走浏览器进程 |
| 每次跑 `Page.navigate` | 复用实例也能回到干净状态，不需要重启 |
| 只认 `file:` 的 page target | 排除扩展的 `background_page` / `service_worker` |
| `cdp.close()` | 只断开 WebSocket，浏览器留给下次 |

真要清理时按 `user-data-dir` 精确匹配，别按进程名杀：

```powershell
Get-CimInstance Win32_Process -Filter "Name='chrome.exe'" |
  Where-Object { $_.CommandLine -match '--headless' -and $_.CommandLine -match 'xinggang-chrome' } |
  ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
```
