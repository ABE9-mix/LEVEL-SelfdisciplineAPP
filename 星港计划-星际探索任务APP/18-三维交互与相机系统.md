## 一、要解决什么

上一版三维区是"永远匀速自转的装饰动画"：球一直在转，用户除了按 `V` 切换两个固定机位，
什么都做不了。这一版要把它做成**能操作的地图**：

| 需求 | 实现 |
|---|---|
| 别一直转 | 待机才转，且降到 0.083 rad/s（约 76 秒一圈） |
| 待机时全景低速度自转 | `globe` 模式 + 2 秒无操作后启动 |
| 拖动旋转 | 单指横向拖动 → 绕竖轴转；纵向拖动 → 改俯角 |
| 点击地表建筑物聚焦 | 射线拾取 → 700ms 过渡到地平线视角 |
| 切换到地平线视图 | `focus` 模式：天空 ≈1/3、建筑在下三分之一 |
| 移动端双指缩放 | 双指捏合改相机距离 |

**核心设计取舍**：相机只有两种模式（`globe` / `focus`）加一个过渡态（`transit`），
不是一个自由度很高的自由相机。原因是课设范围里"自由相机 + 防穿模 + 边界约束"会让调试成本翻倍，
而两个模式已经能覆盖"看全局"和"看一处"这两种真实场景。

## 二、状态机

```
        ┌──────────────────────────────────────┐
        │                                      │
        ▼                                      │
   ┌─────────┐   点建筑（射线命中）    ┌──────────┐
   │  globe  │ ──────────────────────▶ │  focus   │
   │ 全景待机 │                         │ 聚焦一处  │
   └─────────┘ ◀────────────────────── └──────────┘
        ▲         点空白 / Esc                │
        │                                     │
        └───────── transit (950ms) ───────────┘
                    过渡期间不接受输入
```

`transit` 期间相机的**位置与看点**同时 lerp：

```
e(t) = t³(t(6t−15)+10)          // quintic smootherstep
pos  = lerp(from.pos,  to.pos,  e)
look = lerp(from.look, to.look, e)
```

用 lerp 位置 + 看点而不是 lerp 欧拉角，是因为两模式相机朝向差得太多（一个是绕球看、
一个是贴着地表看），角度插值会在中途穿过奇怪姿态。

### 2.1 为什么从 cubic ease-in-out 换成 smootherstep

第一版用 cubic ease-in-out + 700ms，实机观感是"猛地起步 → 冲一下 → 猛地刹住"。
两个原因，各自可量化：

| 曲线 | 峰值速度 / 平均速度 | f″(0.5) |
|---|---|---|
| cubic ease-in-out（旧） | **3.000** | 由 +12 突变为 −12 |
| quintic smootherstep（新） | **1.875** | 0，且全程连续 |

- **峰值速度**：cubic 在中点飙到平均速度的 3 倍（`f'(0.5)=12t²=3`），
  smootherstep 只有 1.875 倍（`f'(t)=30t²(1−t)²`，在 t=0.5 取极大）。
- **jerk（加速度的变化率）**：cubic 的二阶导在 t=0.5 从 +12 跳到 −12，
  这个尖峰正是"冲一下"的体感来源。smootherstep 的 `f''(0)=f''(1)=0` 且连续。

时长同时从 700ms 提到 950ms。实测速度剖面（逐帧采样相机位移）：

```
▁▁▁▂▃▄▅▆▇██████▇▇▆▅▄▃▂▁▁
```

起步与收尾段的最大速度都只有峰值的 22–23%，峰值/平均实测 **1.876**（理论 1.875）。

## 三、globe 全景机位

球面轨道相机，位置由**距离 + 俯角**决定，绕球心：

```js
camera.position = (0, sin(el)·d, cos(el)·d)
camera.lookAt(0, 0, 0)
camera.up = (0, 1, 0)
```

### 3.1 默认距离为什么是 3.6R

视口 390×227，`aspect = 1.72`。球的投影尺寸**受高度约束**（不是宽度）：

| d | 球角直径 | 占屏高 | 结论 |
|---|---|---|---|
| 2.3 | 51.5° | 153% | 裁太多，看不出是球 |
| 3.0 | 38.9° | 112% | 上下略裁 |
| **3.6** | **32.3°** | **92%** | **完整可见且够大** |
| 4.2 | 27.5° | 78% | 偏小 |
| 5.0 | 23.1° | 65% | 太小 |

取 3.6：完整、接近满高、留一点余量给自转时的视觉呼吸。

### 3.2 参数范围

| 项 | 值 |
|---|---|
| 距离 | 2.80 – 5.60 R，默认 3.60 |
| 俯角 | 4° – 58°，默认 18° |
| 待机自转 | 0.055 rad/s（每帧 +0.055/60）≈ 76 s 一圈 |
| 惯性衰减 | 每帧 ×0.92 |

## 四、focus 聚焦机位：以建筑为球心的第二层轨道相机

相机不是钉在一条固定射线上，而是**绕建筑旋转**。步骤：

```js
// ① 建筑处的局部正交基
n  = 该点法线（也是球的径向）
tN = (-sin(lat)·sin(lon), cos(lat), -sin(lat)·cos(lon))   // 朝北切向
tE = n × tN                                                // 朝东

// ② 先算出实测验证过的 home 机位，再换成「相对建筑的偏移」
home = normalize(n − back·tN) · FAC.dist
off  = home − P                     // P = n · FOC_PIVOT_R

// ③ 把 off 在局部基下分解成球坐标 (r, θ₀, φ₀)
r  = |off|
θ₀ = acos( off·n / r )
φ₀ = atan2( off·tE, off·tN )

// ④ 叠加用户拖动量，并夹住极角（见 4.4）
θ = clamp(θ₀ + fPol, 22°, θmax)
φ = φ₀ + fAz

// ⑤ 还原成方向
pos = P + r'·( n·cosθ + (tN·cosφ + tE·sinφ)·sinθ )
      r' = r · S.dist / FAC.dist        // 缩放仍走 S.dist，沿用既有范围

// ⑥ 看向建筑，再绕 right 抬 pitch（把建筑压到画面下三分之一）
dir   = normalize(P − pos)
right = normalize(cross(dir, n))
dir.applyAxisAngle(right, pitch)
look = pos + dir
```

**关键性质**：`fAz = fPol = 0` 时 `pos = P + off = home`、`look = P`，
与原 home 机位**数学上完全相同**，所以 §4.1 那套实测校正过的取景被原样保留
（实测复核：建筑仍在 x=50.0%、y=68.2%，天空仍 35.9%）。

### 4.1 取景参数（实测校正过）

| 参数 | 值 |
|---|---|
| `dist` | **1.10 R** |
| `back` | **0.19 R** |
| `pitch` | **+8°** |
| 缩放范围 | 1.03 – 1.80 R |

**实测结果**（780×454 截图逐像素统计）：

| dist | 天空占比 | 建筑屏位置 y | 建筑色像素数 |
|---|---|---|---|
| 1.05 | 41.0% | 67.5% | 200 |
| **1.10** | **35.9%** | **68.2%** | **1908** |
| 1.15 | 28.4% | 68.9% | 3560 |
| 1.20 | 22.3% | 69.6% | 3695 |
| 1.30 | 14.7% | 70.5% | 4326 |

取 1.10：天空 35.9%（≈1/3），建筑在屏幕 68% 处、可点面积约 1900 像素。

> **枢轴半径为什么取 1.0 而不是设施的 1.006**
> 原 home 机位的 lookAt 就是单位法线方向（半径 1.0）。若把枢轴和看点改成设施网格的
> 1.006，"相机→看点"的仰角会从 21.45° 变成 19.99°，叠上 +8° pitch 后
> 建筑屏位从 68.2% 掉到 **72.3%** —— 实测确实漂了 4%，已改回 1.0。
> 设施盒体实际跨半径 0.986–1.026，1.0 就落在盒体内部，取作枢轴没有问题。

> **为什么不用解析公式直接解**
> 一开始按「天空面积 = 1/3」对半径 1 的球做逐像素求交反解，得到 `dist = 1.20`、
> 预测天空 33.4%。实际渲染出来只有 22.3%。
> 差在**大气壳**：场景里还有一层 `1.035R` 的透明球，它把地平线上方一条天空也盖住了。
> 相机越贴近地表，这层壳占的视角越大，误差越明显。
> 所以解析值只能用来定位区间，最终参数必须按实际渲染帧实测。

### 4.2 `camera.up` 必须换成径向

这一条是**最容易错**的地方：

`camera.lookAt()` 默认用 `up = (0,1,0)`。但 focus 模式下相机贴着 latitude 44–64° 的地表，
该点的径向与该纬度相差 26–46°，用世界 +Y 当地平线会**把地平线转斜**。

实测截图里地平线明显左高右低（中央区高低差 40px / 8.8%）。
换成 `camera.up = 该点径向 n` 之后，地平线才是水平的（中央区高低差降到 26px / 5.7%，
剩下的量是球面本身的曲率，不是倾斜）。

```js
if (S.mode === 'focus')       camUp.lerp(worldNormalOf(S.focusIdx), k);
else if (S.mode === 'transit') camUp.lerp(S.next === 'focus' ? n : WORLD_UP, k * 0.6);
else                           camUp.lerp(WORLD_UP, _followK(20, dtSec));
camera.up.copy(camUp.normalize());
```

（`k` 是跟手系数，见 4.5。）

### 4.3 建筑要做距离补偿缩放（LOD）

建筑世界尺寸 0.028×0.040×0.028 R。透视下屏高 ∝ 1/相机到建筑距离：

| 模式 | 相机到建筑距离 | 建筑屏高 |
|---|---|---|
| focus | ≈0.27 R | ≈55 px |
| globe | ≈2.6 R | ≈4.6 px（看不清也点不准） |

所以按距离反向放大：

```js
const lvScale = clamp((S.dist - 0.95) / 1.4, 1, 3.2);
facs.forEach(m => m.scale.setScalar(lvScale));
```

物理上不正确，但交互上必要——这是游戏里常见的 LOD 手法。

### 4.4 极角夹取（两个约束都要满足）

绕建筑转时 θ 不能无限变，否则会出事：

| 约束 | 说明 | 处理 |
|---|---|---|
| 相机不能钻进大气壳 | 相机半径 ≥ 1.05 R（大气壳 1.035 R） | 按当前 r 反解 θ 上限 |
| `lookAt` 不能退化 | 相机方向与 `up`（= 径向 n）接近共线时 lookAt 会翻 | θ 下限 22° |

θ 上限是**动态**的，因为缩放会改变 r：

```js
const cosLim = (FOC_R_MIN² − FOC_PIVOT_R² − r²) / (2·FOC_PIVOT_R·r);
const thMax  = max(22°, acos(clamp(cosLim, −1, 1)));
```

| 缩放 | r | θ 上限 | 实测相机半径 |
|---|---|---|---|
| 最近 1.03 | 0.205 | 83.0° | 1.0500 R ✓ |
| home 1.10 | 0.219 | 83.0° | 1.0998 R |
| 最远 1.80 | 0.357 | 88°（触到硬上限） | — |

**反算防累积**：夹取后把结果写回 `S.fPol = θ − θ₀`。
若不写回，用户拖过头之后反向拖要先把"虚拟超出的量"拖回来，手感是"粘住"。
实测：在 θ=22.00° 处超拖 6 次后，反向拖 40px 立刻变到 31.17°（Δ=9.17°，与理论值完全一致）。

### 4.5 跟手插值按 dt 归一

原来写死 `camPos.lerp(target, 0.35)`——这是"每帧 35%"，帧率一低就跟不上，
而且和过渡动画的时长口径不一致（一个是时间驱动、一个是帧驱动）。

改成指数衰减形式：

```js
_followK(rate, dtSec) = 1 − e^(−rate·dtSec)
```

`rate = 26` 在 60fps 下 ≈ 0.35；`rate = 22` ≈ 0.30。这样在任何帧率下手感一致。
过渡段本身是时间驱动的（`t = (now − t0) / dur`），不受帧率影响。

## 五、输入处理

### 5.1 只用 Pointer Events

不用 `touchstart/touchmove` + `mousedown/mousemove` 两套。`pointerdown/move/up/cancel`
一套同时覆盖鼠标、触摸、手写笔，`pointerId` 用来区分多指。

```js
T.pointers = new Map()   // pointerId → {x, y}
```

| 事件 | 处理 |
|---|---|
| `pointerdown` | 记入 Map；单指时启动拖动并做一次射线拾取；双指时记录初始间距 |
| `pointermove` | 双指 → 算间距比改 `S.dist`；单指 → globe 改 `S.spin`/`S.el`，focus 改 `S.fAz`/`S.fPol` |
| `pointerup` | 全部抬起时：**且未拖动过**时，有命中 → 聚焦，在 focus 且未命中 → 退回 |

### 5.2 点击与拖动的区分（这里踩过一个坑）

按下时记 `downPos`，移动超过 **6px** 就置 `T.moved = true` 并把候选命中清成 -1。
抬起时**必须同时满足 `!T.moved`** 才当作点击：

```js
if (wasSingle && !T.moved) {
  if (T.downOn >= 0) goFocus(T.downOn);        // 点中建筑 → 聚焦
  else if (S.mode === 'focus') goGlobe();      // 点空白 → 退出聚焦
}
```

第一版只判断了 `T.downOn === -1`，没判断"是否拖动过"。
后果：**聚焦态下随便拖一下、一松手就被踢回全景**（拖动会把 `downOn` 清成 -1，
正好命中"点空白"的分支）。实测表现为 `mode focus → globe`，已修。
现在拖动只是环绕，只有真正的轻点空白才退回。

### 5.3 拾取要用两层

```js
raycaster.intersectObjects(facs, false)   // ① 精确射线
// ② 兜底：屏幕空间最近距离 < 20px 也算命中
```

只靠射线不够：建筑在 globe 下屏幕尺寸只有几个像素，`BoxGeometry` 的三角面很小，
射线必须精确穿过才算命中，手指根本点不到。屏幕空间兜底把命中区放宽到 20px。

### 5.4 双指缩放

```js
k = 初始间距 / 当前间距      // 张开 → k < 1 → 距离变小 → 拉近
S.dist = clamp(初始距离 * k, min, max)
```

注意用**初始距离 × 比例**而不是累乘当前值，否则会因浮点累积产生漂移。

### 5.5 聚焦态拖动 = 绕建筑环绕

| 方向 | 量 | 系数 | 满屏拖动的效果 |
|---|---|---|---|
| 横向 dx | `S.fAz`（方位角） | ×0.008 | 390px ≈ 3.12 rad ≈ 179° |
| 纵向 dy | `S.fPol`（极角） | ×0.004 | 往下拖 = 相机升高 = 更俯视 |

纵向方向与 globe 保持一致：两个模式下"往下拖"都是"相机升高"。

因为 `look` 始终指向枢轴（只加固定 pitch），所以**建筑在任何方位角下都钉在同一屏幕位置**
（实测转 4.48 rad ≈ 257° 后仍是 x=50.0%、y=68.2%），相机↔枢轴半径恒定 0.2185 R
（正圆轨道，实测整圈不变）。

## 七、已知限制

| # | 限制 | 说明 |
|---|---|---|
| 1 | focus 环绕时星球不自转 | 环绕靠移动相机实现，星球保持静止（否则建筑会跑出视锥）。副作用：看不到"建筑自转"的感觉，但这是正确取舍。 |
| 7 | 聚焦态没有"回到 home 机位"的手势 | 退出再进一次才复位。可以补一个双击复位或一个小小的复位按钮。 |
| 8 | 枢轴固定在球面点，不跟随建筑 LOD 缩放 | 建筑在 globe 下被放大 3.2×，聚焦时缩回 1×，视觉上有个跳变。可加过渡。 |
| 2 | 没有点击涟漪 / 高亮反馈 | 选中态只是切换视角，建筑本身没有视觉变化。设计稿阶段应该补一个脉冲光圈。 |

| 6 | 未处理多指与页面滚动冲突 | 已加 `touch-action: none`（在 `#stage` 上）；但整个页面若后续改成可滚动，需要重新验证手势归属。 |

## 八、答辩可讲的点

> "三维视窗不是一段循环动画，是一个有状态的地图。全景可以拖、可以缩放，
> 点地表建筑就飞过去——这个过程是 950ms 的 smootherstep 缓动过渡，不是硬切。
> 聚焦之后还能绕着建筑转圈，建筑始终钉在同一个屏幕位置。
>
> 过渡曲线我换过一次：第一版用 cubic ease-in-out，体感是'冲一下'。
> 量化下来，cubic 的峰值速度是平均速度的 3 倍，而且二阶导在中点从 +12 跳到 −12；
> 换成 smootherstep 之后峰值只有 1.875 倍、二阶导连续，逐帧测出来的速度剖面
> 起步和收尾都只到峰值的 22%。
>
> 几个坑都是实测发现的：`lookAt` 默认用世界 Y 当上方向，建筑在中高纬度时
> 地平线会歪 40px，改成用该点径向才正；聚焦的取景距离我按天空占 1/3 反解出 1.20R，
> 实际渲染只有 22%，查出来是大气壳挡了一部分天空，校正到 1.10R 才得到 35.9%；
> 轨道枢轴我一开始用了设施的 1.006，取景漂了 4%，改回球面 1.0 才对齐。"
