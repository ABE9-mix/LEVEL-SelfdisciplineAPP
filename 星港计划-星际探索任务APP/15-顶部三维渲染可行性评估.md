# 15 · 顶部三维渲染可行性评估（WebGPU / three.js 内嵌）

> ⚠️ **课设版请先看 [16-课设版实现范围与答辩要点](16-课设版实现范围与答辩要点.md)**。
> 本文按「要上线的产品」写（6 机型实测、内存/耗电预算、WebView 风险治理）；
> 课设只需要其中「渲染负荷」与「选型结论」两节，其余**延期，不进课设范围**。
> 保留全文的价值：答辩时证明"知道生产级要考虑什么"。

> **评估对象**：主页面顶部「星球视窗」（IA v2），不是全屏三维地图。
> **结论先行**：**性能不是瓶颈，three.js 内嵌可行且推荐作为基线；WebGPU 不应作为验收依赖，只作可选加速路径。**
> 本文所有数字都可由脚本复算；标「待实测」的项必须在真机上测，不允许按经验拍板。

## 一、结论摘要

| # | 结论 | 依据 |
|---|---|---|
| 1 | **渲染负荷只有原规划的 1/5**，视口占屏 19.6%（358×180），稳态 3.2 万三角面 | 见 §二、§三 |
| 2 | **WebGL2 就够，WebGPU 不是必需品** | GPU 单帧 0.35–0.93 ms，预算 16.7 ms |
| 3 | **WebGPU 覆盖率是硬伤**：iOS 17/18 设备没有，Android WebView 默认开启与否待实测 | §四 |
| 4 | **不要用 Unity/Godot**：为 3.2 万面付 30–60 MB 包体不划算 | §五 |
| 5 | **真正要盯的是 WebView 首帧、内存、上下文丢失**，不是帧率 | §六 |
| 6 | **存在一条更便宜的降级路：2.5D 预渲染转盘**，358×180 下可能视觉等价 | §五 方案 E、§七 降级触发条件 |

**一句话建议**：用 **three.js + WebGL2** 做基线（覆盖 >99% 设备），把着色器写成 TSL、渲染器换成 `WebGPURenderer` 就能在支持的设备上吃 WebGPU 而不改业务代码——但**验收标准里不写 WebGPU**。

## 二、需求重新基线（这一步改变了全部结论）

原 10 章的三维预算（15 万三角面、全屏 60fps）写在「星球地图即主界面」的假设上。IA v2 已把三维收缩为**顶部固定视窗**：

| 项 | 旧假设（10 章） | 现设计（IA v2 + 线框稿） | 变化 |
|---|---|---|---|
| 三维区域 | 全屏 390×844 | **顶部 358×180** | 面积降到 **19.6%** |
| 相机 | 可旋转缩放看全貌 | 固定位姿，球体自转 | 不可交互 → 无需 LOD 切换逻辑 |
| 设施可见数 | 全部（20+） | 视窗内可见 2–8 个 | 稳态 LOD 更省 |
| 交互 | 点设施、拖拽选址 | 仅点击进入（可选） | 输入事件极少 |
| 是否参与滚动 | 否 | **否（固定在顶部）** | 规避 WebView 滚动嵌坑 |

**像素量与填充**（脚本计算）：

| 渲染倍率 | 视口物理像素 | 含 2× 过绘制 | GPU 填充耗时（保守下限） |
|---|---|---|---|
| DPR 2.0 | 716×360 = 0.258 Mpx | 0.52 Mpx | 0.34 ms |
| DPR 3.0 | 1074×540 = 0.580 Mpx | 1.16 Mpx | 0.77 ms |
| **封顶 1.5×** | 537×270 = 0.145 Mpx | 0.29 Mpx | **0.19 ms** |
| 封顶 2.0× | 716×360 = 0.258 Mpx | 0.52 Mpx | 0.34 ms |

> 建议：**渲染倍率封顶 2.0×，默认 1.5×**。358×180 的小视窗用 DPR3 渲染纯属浪费——小视窗里像素密度收益远小于耗电代价。

## 三、渲染负荷与每帧预算

### 3.1 三角面

| 组成 | 规格 | 三角面 |
|---|---|---|
| 星球球体 | 64×32 分段 | 4,096 |
| 设施 LOD0 × 2（视窗内近景） | 8,000 each | 16,000 |
| 设施 LOD1 × 4 | 2,500 each | 10,000 |
| 设施 LOD2 × 6（远端/未激活） | 350 each | 2,100 |
| **稳态合计** | | **32,196** |

对比 10 章原预算 15 万面 → **实际只需 21.5%**。

补充：球体细分不必上 128×64（16,384 面）。358×180 视窗里球的屏幕直径约 150–180 pt，**64×32 已看不出棱角**；若贴图带位移/法线可再降到 48×24（2,304 面）。

### 3.2 每帧总预算（60 fps = 16.7 ms）

| 环节 | 估算区间 | 说明 |
|---|---|---|
| GPU 光栅化 | 0.3 – 0.8 ms | 3.2 万面 + 0.1–0.6 Mpx |
| three.js JS 侧 | 0.4 – 1.2 ms | 矩阵更新、~20 draw call |
| WebView 合成画布 | 0.8 – 2.0 ms | WebView 特有开销，最大不确定项 |
| 主线程 UI/其它 | 0.5 – 1.5 ms | 原生 UI + HUD |
| **合计** | **2.0 – 5.5 ms** | 60fps 余量 ≥ 11.2 ms |

**判据**：即使每项取上限，也只占 60fps 预算的 1/3。若实测超出，问题一定在 WebView 集成层（合成、首帧、上下文），不在渲染本身。

### 3.3 耗电（30 fps 常开，视口固定）

| 设备档 | 估算 | 备注 |
|---|---|---|
| 中端 Android | ≈ 4.5 %/h | WebView + 轻 3D + 屏幕本身 |
| iPhone 中端 | ≈ 3.8 %/h | WKWebView 合成效率较好 |
| 旗舰 | ≈ 2.8 %/h | — |

**必须做的省电动作**（成本低、收益大）：

| 动作 | 效果 |
|---|---|
| 视窗滚出屏幕 / App 进后台 → `cancelAnimationFrame` | 后台归零 |
| `idle` 8 秒后从 60fps 降到 30fps | 省约 40% GPU |
| 熄屏 → 停帧 | 归零 |
| 低电量模式 → 降到 20fps + 1.0× 渲染倍率 | 省约 60% |
| 静态遮挡（如弹窗全屏）→ 暂停 | 归零 |

### 3.4 资源体积

| 项 | 体积 | 优化 |
|---|---|---|
| three.js（tree-shake 后，仅 sphere/basic/KTX2/GLTF） | ≈ 0.17 MB | 用 `three/webgpu` 子包按需引入 |
| 应用侧 3D 逻辑 | ≈ 0.30 MB | — |
| 星球等距柱状贴图 | 2048×1024 RGBA8 = 8.4 MB 原始 → **KTX2/ASTC 约 1.5 MB** | 必须压缩纹理，否则显存与包体双爆 |
| 设施 GLB × 8 | ≈ 1.2 MB | Draco + KTX2 |
| **三维部分合计** | **≈ 3.2 MB** | |
| 对比 Unity 最小包 | 30–60 MB | 为用户只看的 358×180 付这个代价不划算 |
| 对比 Godot 4 导出 | 15–25 MB | 同上 |

| 平台 | WebGL2 | WebGPU | 置信度 | 动作 |

| **iOS WKWebView 26+** | ✅ | ⚠️ **待实测** | **低** | **必测**：WKWebView 未必与 Safari 同步开启该特性 |
| iOS 15–18（Safari/WKWebView） | ✅ | ❌ | 高 | 若最低支持 iOS 16/17 → **WebGPU 不可依赖** |

| **Android WebView（Chromium 121+）** | ✅ | ⚠️ **待实测** | **低** | **必测**：WebView 特性开关与 Chrome 不完全一致，且受厂商 ROM 影响 |

| 桌面浏览器（原型阶段） | ✅ | ✅ | 高 | 原型阶段可直接用 |

### 4.1 三行检测代码（贴到任何 WebView 里跑）

```js
console.log('WebGPU 存在:', !!navigator.gpu);
const gl = document.createElement('canvas').getContext('webgl2');
console.log('WebGL2 存在:', !!gl, gl && gl.getParameter(gl.VERSION));
if (navigator.gpu) {
  navigator.gpu.requestAdapter().then(a => console.log('适配器:', a ? (a.info?.description || 'ok') : 'null'));
}
```

**判定规则**：
- `navigator.gpu` 存在 **且** `requestAdapter()` 返回非 null → 该设备可用 WebGPU
- 存在但 adapter 为 null → 典型「API 有、驱动不支持」，**必须降级**（这是最常见的坑，只查 `navigator.gpu` 会误判）

## 五、五个方案对比

| # | 方案 | 包体增量 | 首帧 | 性能 | 开发成本 | 覆盖率 | 适合 |
|---|---|---|---|---|---|---|---|
| **A** | **WebView + three.js（WebGL2）** | ≈ 3.2 MB + WebView 基线 | 200–600 ms（可预热） | 足够（§三） | 低（一套代码） | **>99%** | ✅ **推荐基线** |
| **B** | WebView + three.js（`WebGPURenderer`，WebGPU 优先 / WebGL2 回退） | 同 A（+~0.1 MB） | 同 A | 略优（大场景才明显） | 低（TSL 一套着色器） | 同 A（自动回退） | ✅ **A 之上零成本叠加** |
| C | 原生 Metal（iOS）+ GLES（Android） | ≈ 0.5 MB（无 WebView） | 最快（<100 ms） | 最优 | **高（两套实现）** | 100% | 后期若要全屏三维再考虑 |
| D | 原生 WebGPU（Dawn，C++ 单 API） | ≈ 5–10 MB | 快 | 优 | 很高（iOS/Android 双构建链） | 取决于 Dawn 支持 | ❌ 3.2 万面不值得 |
| E | **2.5D 预渲染**（球体转盘序列帧/视频 + 设施精灵分层合成） | ≈ 1–2 MB | **最快（几十 ms）** | 无 GPU 依赖 | 最低 | **100%** | ⚠️ **降级备选，见 §七** |
| F | Unity URP / Godot 4 | 30–60 MB / 15–25 MB | 1–2 s | 过剩 | 中 | 100% | ❌ 用户已否，数据也支持否 |

### 5.1 为什么 WebGPU 对本案收益极小

WebGPU 的价值在**大规模绘制、计算着色器、多线程提交**。本案：

| WebGPU 优势 | 本案是否需要 |
|---|---|
| 更低 draw call 开销 | 只需 ~20 个，WebGL2 已无压力 |
| Compute Shader（粒子/后处理） | 不需要（无粒子、无后处理） |
| 多线程命令录制 | 不需要（单视窗） |
| 更好的功耗管理 | 可能小幅受益，但远小于「降帧率+降倍率」的收益 |

**结论**：WebGPU 在本案**只带来个位数性能收益，却引入一整条不可用分支**。用 TSL 写着色器是为「以后能无痛切过去」留的门，不是现在必须走的路。

## 六、WebView 特有的 8 个工程风险

这些才是真正会让方案翻车的点（帧率不是）。

| # | 风险 | 表现 | 对策 | 严重度 |
|---|---|---|---|---|
| 1 | **首帧慢** | 冷启后 300–800 ms 黑块/白块 | ① App 启动即创建 WebView 并预热空白页；② 首帧前显示**静态星球图**占位（与终态同帧，视觉无感切换）；③ `renderer.compile()` 预编译着色器 | 高 |
| 2 | **内存占用** | WebView 基线 60–120 MB + GPU 缓冲 20–40 MB | ① 单例 WebView 全 App 复用；② 离开主页面不销毁但 `cancelAnimationFrame`；③ 贴图 KTX2 压缩，纹理总量 ≤ 4 MB | 高 |
| 3 | **上下文丢失** | iOS 后台回收显存 → 回前台黑屏 | 监听 `webglcontextlost` / `webgpu` device lost → **销毁并用静态图占位，200 ms 内重建**；不要试图 restore | 高 |
| 4 | **后台节流** | rAF 在后台自动停 → 反而不是问题 | 显式在 `visibilitychange` 停帧，避免恢复时突刺 | 低 |
| 5 | **Android 滚动嵌坑** | WebView 放在可滚动容器里会「手势打架、滚动卡顿」 | **本设计天然规避**：视窗固定在顶部不参与滚动（IA v2 已如此）。任何「把 3D 放进列表」的改动都要否决 | 中（已规避） |
| 6 | **触摸事件冲突** | 视窗拦截了页面滑动 | 视窗仅响应点击（进入），`touch-action: pan-y` 放行纵向滚动 | 中 |
| 7 | **纹理/显存上限** | 老 Android 显存小，2048² 图集可能失败 | 图集降到 1024²（设施为像素/低模，够用）；启动时查 `MAX_TEXTURE_SIZE` | 中 |
| 8 | **离线可用** | 首启无网时 CDN 加载失败 | **three.js 与资源必须打进本地包**，禁止运行时从 CDN 拉 | 高 |

### 6.1 首帧预算（建议写入验收）

| 阶段 | 目标 | 做法 |
|---|---|---|
| App 冷启 → 主页面可见 | ≤ 1.2 s（不含 3D） | 原生 |
| 主页面可见 → 3D 首帧 | **≤ 400 ms**，且此期间显示**同帧静态图** | 预热 + 预编译 + 占位图 |
| 用户感知的「3D 出现」 | **无跳变** | 占位图与首帧对齐（同机位、同光照相位） |

> 这条「静态图占位」是让 WebView 方案在体验上追平原生的关键技巧：用户永远看不到黑块，只会看到画面「活过来」。

## 七、推荐路线与决策门

### 7.1 三阶段

| 阶段 | 内容 | 产出 | 时间 |
|---|---|---|---|
| **S0 可行性实测** | 【课设不需要】跑 6 机型打表；课设只跑演示机一台（见 16 章） | 一张实测表（§八） | 0.5 天（课设：0） |

| **S2 硬化** | 占位图切换、上下文丢失恢复、省电策略、低端降档 | 达到验收门 | 3–4 天 |

### 7.2 决策门（全过才走 three.js 路线）

| # | 指标 | 阈值 | 不过怎么办 |
|---|---|---|---|
| G1 | 中端安卓（3 年前机型）交互帧率 | p95 ≥ 50 fps @30fps 模式 | 降渲染倍率至 1.0× + 减设施面数 |
| G2 | 主页面可见 → 3D 首帧 | ≤ 400 ms | 预渲染首帧做静态图，3D 延后 1 秒静默启动 |
| G3 | 内存增量（相对无 3D） | ≤ 70 MB | 降纹理、销毁重建 |
| G4 | 待机耗电 | ≤ 5 %/h | 降帧率到 20fps、视窗缩小动画 |
| G5 | 上下文丢失恢复 | ≤ 300 ms 且有占位图 | 改为「离开即销毁，回来重建 + 静态图」 |
| G6 | WebGPU 分支（若做 B） | 不得导致 WebGL2 路径回归 | **直接砍掉 WebGPU 分支**（它本就不是必需） |

### 7.3 **什么情况下应当放弃三步并退到方案 E**

若出现下列任一情况，2.5D 预渲染反而是正确选择：

| 触发条件 | 为什么退 |
|---|---|
| 最低支持 iOS ≤ 18 **且**产品要求三维「必须**可旋转/可缩放**」 | WebView 覆盖率与交互都要打补丁，成本超过收益 |
| G2/G3 连续两轮不过（预热+压缩后仍 >400 ms / >70 MB） | 说明目标机型 WebView 太重 |
| 设施视觉确定为**固定 8 种形制 × 5 级 = 40 个状态**且不变 | 转盘序列帧 + 状态叠层即可穷举，无需实时渲染 |
| 需要「绝对一致的像素风观感」（项目已有 NES 像素规范） | 预渲染可先在设计侧逐像素审定，实时渲染难以保证 |

**方案 E 的具体形态**（若走到这一步）：
- 星球自转：**预渲染 240 帧循环序列（12s @20fps）**，或一条透明 WebM/HEVC 循环
- 昼夜相位：预渲染 6 套（晨/昼/昏/夜/深夜/极），或单套 + 颜色叠加
- 设施：每种形制/等级一张精灵图，按球面坐标做**球面投影定位** + 缩放，叠在转盘上
- 体积：240 帧 × 358×180 × KTX2 ≈ 1.2–2 MB
- 代价：设施灯光状态需额外叠层；无法做「实时脉冲/晨昏推进」这类动态效果（可降级为叠加淡入）
